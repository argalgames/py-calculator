> is it ideal to delete the branch after merge?

● Yes, it's normal and recommended to delete a feature branch once it's merged.

  Why:
  - Its commits are already in main, so deleting the branch loses nothing. The
    commits stay in history, and GitHub lets you restore the branch from the PR
    page if you ever need it.
  - Your branch list stays short, so you can tell which work is still in
    progress.
  - It stops you from accidentally committing to an old branch that's already
    been merged.

  How:

  1. On GitHub: after merging, the PR page shows a Delete branch button. You can
     also turn on Settings → General → "Automatically delete head branches" so
     GitHub deletes them for you.
  2. Locally:
  git checkout main
  git pull
  git branch -d addition-feature
     Lowercase -d is the safe version: Git refuses to delete the branch if it
     hasn't been merged. Avoid -D unless you really mean to throw away the work.

     If you merged on GitHub with "Squash and merge" or "Rebase and merge", -d
     may say the branch isn't fully merged even though it is. Once you've
     checked the PR shows as merged, -D is fine in that case.
  3. Clean up references to deleted remote branches:
  git fetch --prune

  Workflow: one branch per feature. Create it from main, open a PR, merge it,
  delete it, and repeat for subtraction-feature.

  5b: Why it happens

  When Python imports a file, it runs the whole file from top to bottom. The def
  lines only define functions, which is harmless. But the code at the bottom
  (get_number(...), print(...)) actually runs, so importing calculator starts
  the program.

  This is a problem because tests in Step 6 will do from calculator import add.
  A test that stops and waits for keyboard input would hang.

  5c: The fix, __name__

  Python gives every file a built-in variable called __name__:

  ┌──────────────────────────────────────┬───────────────────┐
  │         How the file is used         │ Value of __name__ │
  ├──────────────────────────────────────┼───────────────────┤
  │ Run directly: python calculator.py   │ "__main__"        │
  ├──────────────────────────────────────┼───────────────────┤
  │ Imported: from calculator import add │ "calculator"      │
  └──────────────────────────────────────┴───────────────────┘

  You can check this by adding print(__name__) at the top of calculator.py and
  running both ways. Remove it afterwards.

  So this line means "only run this when the file is run directly":

  if __name__ == "__main__":
    ...

  6e: A floating-point surprise

  Add this test and run it:

  It fails, because computers store decimals in binary, and 0.1 + 0.2 comes out

  import pytest

  def test_add_decimals_precision():
    assert add(0.1, 0.2) == pytest.approx(0.3)

● You're close. The if/elif part is right. The while loop has three problems:

  Problem 1: operator != "+" or "-" is always true

  This is one of the most common Python bugs. Python doesn't read it as
  "operator is not + or -". It reads it as:

  (operator != "+") or ("-")

  and a non-empty string like "-" always counts as True. So the whole condition
  is always True, and the loop would never end.

  You can test it yourself in the terminal by running python and typing:

  >>> operator = "+"
  >>> operator != "+" or "-"

  Two correct ways to write the check:

  operator != "+" and operator != "-"   # spell out both comparisons

● No, this test fails. Here's the pytest output:

  Obtained: 0.6666666666666666
  Expected: 0.67 ± 6.7e-07

  Why

  pytest.approx doesn't mean "roughly the same". By default it allows a
  difference of only about one part in a million of the expected value. That's
  the ± 6.7e-07 in the output. It's meant to absorb tiny floating-point noise
  like 0.30000000000000004, not to round to 2 decimal places.

  0.67 is about 0.0033 away from the real answer, which is far more than the
  allowed 0.00000067.

  How to fix it

  Pick one of these options:

  # Option 1: write the expected value with enough decimal places
  assert divide(2, 3) == pytest.approx(0.6666667)

  # Option 2: keep 0.67 but set your own tolerance explicitly
  assert divide(2, 3) == pytest.approx(0.67, abs=0.01)

  Option 1 is the better test. Option 2 would also pass if divide returned
  0.675, which is wrong.

  One thing to avoid: pytest.approx(2 / 3). It passes, but it just repeats the
  code's own calculation, so it would still pass if divide were wrong in the

> I cannot see the step 2 in vs code for the requirements.txt format

● The encoding label is easy to miss, and it's hidden entirely if the status bar
  is turned off. You can reach the same option from the Command Palette:

  1. Open requirements.txt and make sure the editor has focus (click inside the
     file).
  2. Press Ctrl+Shift+P.
  3. Type Change File Encoding and press Enter.
  4. Choose Save with Encoding.
  5. Choose UTF-8 from the list. Pick plain "UTF-8", not "UTF-8 with BOM".

  Where the status bar label normally is: the blue or purple bar along the very
  bottom of the VS Code window, on the right, near Ln 1, Col 1, CRLF, and Plain
  Text. If there's no bar at all, turn it on with View → Appearance → Status
  Bar.

  Or recreate the file from the terminal

  With the venv active, this rewrites the file as UTF-8:

  python -m pip freeze | Out-File -Encoding utf8 requirements.txt

  Be aware that PowerShell 5.1's utf8 option adds a BOM (an invisible marker at
  the start of the file). pip handles it fine, but the VS Code steps above give
  a cleaner result.

  Check it worked

  git diff --stat

  Or reopen the file. The text should look normal, and the status bar label
  should say UTF-8 instead of UTF-16 LE. Then commit both files as in my
  previous message.
